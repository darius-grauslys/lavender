PLATFORM_coredump — core/include/platform.h

Attempts to produce a platform-specific core dump (memory dump) so the caller (`debug_error`) can "create core dump, but keep going"; declared in the core header with no implementation in `core/` itself — each backend provides its own, by design, per the header comment (lines 13-19) which states that all `PLATFORM_*` functions are implemented by backends such as SDL, nds, no_gui, or a test harness.

Pre-conditions:
1. None. The function takes no parameters (`void PLATFORM_coredump(void)`) and performs no pointer dereferencing on caller-supplied data, so no input validation, null-check, or range-check pre-conditions apply.
2. The caller must be in a context where generating a core dump (and, on some backends, continuing execution afterward) is acceptable. The sole core caller is `debug_error` in `core/source/debug/debug.c:76`, which invokes it unconditionally after printing the error message, relying on the function returning so execution may continue (see the comment on line 75: "create core dump, but keep going"). The decision to attempt a coredump is the caller's responsibility.

Post-conditions:
1. On the POSIX/SDL/no_gui/test/template backends (`sdl/source/debug/sdl_debug.c:5`, `no_gui/source/debug/no_gui_debug.c:5`, `tests/core/source/PLATFORM.c:169`, `tests/templates/source/PLATFORM.c:169`), the function forks; the child process calls `abort()` (raising SIGABRT and generating a core dump), while the parent process returns normally so `debug_error` can continue. No `wait()`/reaping of the child is performed by this function; if `fork()` fails (returns -1), the function returns without aborting any process.
2. On the NDS backend (`nds/source/debug/nds_debug.c:6`), the function emits a verbose warning ("PLATFORM_coredump not defined on nds.") and then calls `PLATFORM_abort()` (which performs a memory-mapped hardware reset at address 8192 and does NOT return). This contradicts the "keep going" semantics relied upon by `debug_error`, but is a graceful platform-specific degradation: the NDS has no filesystem core-dump facility, so abort/reset is the closest available behavior.
3. The function does not clean up, mutate, or free any Lavender-owned data structures, pools, or allocated memory.

Correctness Verdict: Correct

Semantic Alignment:
The function faithfully fulfills its declared intent as the engine's core-dump hook. It is declared in `core/include/platform.h` (line 69) alongside `PLATFORM_pre_abort` and `PLATFORM_abort`, and is documented in `agents/platform_api.md` ("Backend writes a memory dump") and the debug module docs (`agents/core/modules/debug.md`, which notes `PLATFORM_coredump` is "called by `debug_error` after the message; execution continues if the hook returns"). On the POSIX/SDL/no_gui/test/template backends, the fork-then-`abort()` pattern is a sound way to produce a core dump for the child while letting the parent (the running engine) continue — matching the "keep going" intent. There is no implementation in `core/` itself, which is by design (header comment lines 13-19). The only semantic deviation is on the NDS backend, where `PLATFORM_coredump` delegates to `PLATFORM_abort` (a non-returning hardware reset) because the NDS platform cannot produce a real core dump; this is a known, intentional graceful degradation rather than a bug. No semantic drift or omission is present on the mainstream (POSIX/SDL) backends.

Implementation Correctness:
- Type compatibility: The signature is `void PLATFORM_coredump(void)`, taking no parameters and returning nothing. All backend implementations match this signature exactly — no implicit conversions, no truncation, no type mismatch. In the POSIX/SDL/no_gui/test/template backends, `fork()` returns `pid_t` and `abort()` has prototype `void abort(void)`; the `!fork()` check applies the integer logical-not to a `pid_t`, which is well-defined and exact. In the NDS backend, `debug_warning__verbose` and `PLATFORM_abort()` are both `void`-returning functions, correctly sequenced.
- Undefined behavior: On the POSIX/SDL/no_gui/test/template backends, `fork()` is a standard POSIX call and `abort()` is standard C — no broken pointer arithmetic, no null dereference, no type punning, no out-of-bounds access. The `!fork()` idiom correctly identifies the child (fork returns 0) which then calls `abort()`; a `fork()` failure (-1) is treated as "not the child" so neither side aborts, which is safe (not UB). On the NDS backend, the only effect is a verbose log print and a call to `PLATFORM_abort()`, whose memory-mapped write is confined to the bare-metal NDS address space (see PLATFORM_abort review) and is not generic out-of-bounds access. There is no UB on any backend.

The decision to generate a coredump is the caller's (`debug_error`) responsibility. Note: the fork-then-abort pattern does not `wait()` on the child, so a terminated child becomes a short-lived zombie until reaped by init (or parent exit); this is acceptable for a debug-only hook and is not a correctness defect.
