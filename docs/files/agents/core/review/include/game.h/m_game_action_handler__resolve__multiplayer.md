m_game_action_handler__resolve__multiplayer — core/source/game.c, lines 86-89 (decl) and 850-869 (impl)

Routes a Game_Action through the multiplayer resolution policy: an unallocated action is treated as already resolved (returns true), a local action is delegated to the singleplayer resolver, and any other (non-local, multiplayer) action is released from its owning Client's game-action pool.

Pre-conditions:
1. p_game_action is dereferenced by the very first predicate. However, is_game_action__allocated() (game_action.h:48) is null-safe — it short-circuits on a NULL pointer and returns false. Therefore p_game_action MAY be NULL and the function safely returns true without dereferencing it further. When p_game_action is non-NULL, it must point to a valid, readable Game_Action; by the time is_game_action__local() (which does NOT null-check, game_action.h:115) is reached, p_game_action is guaranteed non-NULL because is_game_action__allocated() returned true, which itself requires a non-NULL pointer. (This is the correct, null-safe predicate ordering — it differs from m_game_action_handler__dispatch__multiplayer, where is_game_action__local() is called at the top with no prior null guard.)
2. p_client's requirement depends on the action's classification. On the local-action path, p_client is forwarded to m_game_action_handler__resolve__singleplayer, whose own null guard returns false (logging a debug_error) when p_client is NULL. On the non-local multiplayer path, p_client is required to be non-NULL: a NULL p_client here returns false with no release.
3. p_game is NOT dereferenced anywhere in this function body, nor by the direct callees reached on either branch (m_game_action_handler__resolve__singleplayer ignores p_game; release_game_action_from__client takes only p_client and p_game_action). Consequently p_game carries no null-dereference risk within this function, though callers conventionally pass a valid Game for API consistency.

Post-conditions:
1. Returns true immediately if the action is not allocated (including when p_game_action is NULL). No release, and no side effect, occurs on this path.
2. For a local action: returns the result of m_game_action_handler__resolve__singleplayer(p_game, p_client, p_game_action). If p_client is NULL this returns false and logs "m_game_action_handler__resolve__singleplayer, p_client == 0."; otherwise it releases the action from p_client's pool and returns true.
3. For a non-local multiplayer action with a NULL p_client: returns false and performs no release — the action is left in its allocated state (a failed resolution). Note this differs from the singleplayer path: no debug_error is logged here (only the return value changes), an inconsistency flagged in Implementation Correctness.
4. For a non-local multiplayer action with a non-NULL p_client: returns release_game_action_from__client(p_client, p_game_action), which releases the action — selecting the inbound/outbound Game_Action_Manager by the action's IS_IN_OR_OUT_BOUND flag and resetting the action's Serialization_Header to a deallocated state so its slot is returned to the pool (Lavender-style initialization).
5. The Game_Action argument is mutated only on the successful release paths (cases 2 and 4): its serialization header is reset to a deallocated state. In the not-allocated, local-null-client, and non-local-null-client-failure paths the action is left unchanged (or was already unallocated).

Correctness Verdict: Correct

Semantic Alignment:
The implementation fulfills its resolve intent. The three-way branch — not-allocated → done, local → singleplayer resolver, else → release-from-client — matches the multiplayer resolution policy, and each branch correctly returns the delegated callee's bool result. The predicate ordering is safe (the null-tolerant is_game_action__allocated() runs before the null-unsafe is_game_action__local()). The single semantic caveat is the logging asymmetry between the two false-returning failure paths (see Implementation Correctness below); it is an inconsistency in defensive diagnostics, not a drift in what the function computes — the function does exactly what its policy intends.

Implementation Correctness:
- Type compatibility — p_game (Game *), p_client (Client *), and p_game_action (Game_Action *) match the parameter types of m_game_action_handler__resolve__singleplayer(Game *, Client *, Game_Action *) and release_game_action_from__client(Client *, Game_Action *) exactly. The propagated bool return values are returned directly. No implicit conversions or truncation occur.
- Undefined behavior — no pointer arithmetic, no type punning, no out-of-bounds access in this function. The only dereference risk is the p_game_action predicates: that risk is eliminated because is_game_action__allocated() is called first and is null-safe, guaranteeing p_game_action is non-NULL before is_game_action__local() dereferences it. p_client is only ever (transitively) dereferenced by release_game_action_from__client, which is reached only after p_game is non-NULL on the non-local path and only after m_game_action_handler__resolve__singleplayer's own null guard on the local path. p_game is never dereferenced here or on these direct callee paths. No UB.
- Validation — p_client is appropriately validated on the non-local path (NULL → false) because the release callee cannot tolerate a NULL client. p_game_action is effectively validated by the null-safe is_game_action__allocated() check. p_game requires no validation because it is not dereferenced. One minor validation gap: the non-local NULL-p_client path silently returns false without logging, whereas the sibling singleplayer path and m_game_action_handler__dispatch__multiplayer's unicast path both emit a debug_error here. This is a diagnostic consistency issue, not a correctness defect — the failure is still surfaced via the return value.

Side Effects:
- On the local-action path: delegates to m_game_action_handler__resolve__singleplayer, which (a) may emit a debug_error log line when p_client is NULL, and (b) on success calls release_game_action_from__client, resetting the action's serialization header to a deallocated state so the slot returns to the pool.
- On the non-local multiplayer path with a non-NULL p_client: calls release_game_action_from__client, releasing the action through the client's appropriate (inbound or outbound) Game_Action_Manager — resetting the action's serialization header to deallocated and returning its slot to the free pool.
- On the not-allocated path (including NULL p_game_action): no side effects; returns true.
- On the non-local path with a NULL p_client: no side effects; returns false without logging (the action is left allocated).
- No direct mutation of Game occurs: p_game is not dereferenced on either branch, and the only Game_Action mutation happens through the delegated release. The function itself emits no debug_error log lines of its own.

Lavender-Specific Semantics — Initialization ≠ RAII:
The release performed here routes through release_game_action_from__client → release_game_action_from__game_action_manager → initialize_serialization_header_for__deallocated_struct. This is Lavender-style initialization in the pool-cleanup sense: it clears the Game_Action to its initial conditions so the slot can be returned to a free pool for reuse, rather than RAII resource teardown. m_game_action_handler__resolve__multiplayer participates correctly in this pattern — it does not acquire or tear down resources itself; it simply routes the action to the owning client's manager for the reset, or short-circuits when there is nothing to release.
