PLATFORM_get_time_elapsed — core/include/platform.h

### Semantic
Returns the wall-clock time elapsed since the previous call, as a `u32F20` fixed-point value in binary seconds (20 fractional bits), and in-place advances the two `Timer__u32` accumulators that track absolute seconds and sub-second nanoseconds.

The header holds only the declaration; concrete implementations live in the platform backends: SDL (`sdl/source/time/sdl_time.c`), no_gui (`no_gui/source/time/no_gui_time.c`, duplicated verbatim in the test stub `tests/core/source/PLATFORM.c`), and NDS (`nds/source/time/nds_timer.c`). `PLATFORM_initialize_time` captures the baseline against which the delta is measured (a no-op on the Windows/timeGetTime backends, which instead derive the delta from the `Timer__u32`'s stored prior value).

### Pre-conditions
1. `p_timer__seconds__u32` must be non-null and point to a `Timer__u32` initialized via `initialize_timer_u32` with `start = remaining = UINT32_MAX` (established by `initialize_game`).
2. `p_timer__nanoseconds__u32` must be non-null and point to a `Timer__u32` initialized via `initialize_timer_u32` with `start = remaining = 999999999` (established by `initialize_game`).
3. On SDL/no_gui-Unix backends, `PLATFORM_initialize_time` must have been called before the first `PLATFORM_get_time_elapsed` call, so the module-level baseline (`_SDL_miliseconds_last` / `_NO_GUI_timespec__initial`) is established.
4. The timer `start` must be non-zero (guaranteed by the sentinels in pre-conditions 1-2). `progress_timer__u32` performs `quantity %= start`; with `start == 0` this is undefined behavior (division by zero), which is why the `UINT32_MAX` / `999999999` sentinels are load-bearing.

### Post-conditions
1. Returns a `u32F20` value representing elapsed seconds since the previous call (binary fixed-point, 20 fractional bits). On the first call the delta is measured from the `PLATFORM_initialize_time` baseline.
2. `p_timer__seconds__u32` and `p_timer__nanoseconds__u32` are advanced in-place via `progress_timer__u32`, mutating their `start - remaining` ("elapsed-ticks") reading.
3. On backends using a module-level baseline, the baseline is updated to the current timestamp.

### Correctness Verdict
Incorrect

The declaration itself is well-formed (`u32F20` = `uint32_t`; two `Timer__u32 *` parameters), but the shipped implementations contain defects that violate the documented semantic on specific backends (see Implementation Correctness).

### Semantic Alignment
Intention: return elapsed time since last call as u32F20 and advance the two timer accumulators. The SDL non-Windows path (`sdl/source/time/sdl_time.c:60`) fulfills this: it returns `elapsed_miliseconds << 10` (a binary-seconds approximation consistent with the engine's 20-bit fixed-point convention) and advances both timers. The Windows/timeGetTime paths (`sdl_time.c:18`, the no_gui `_WIN32` branch, and the test stub's `_WIN32` branch) return `((elapsed_miliseconds & MASK(10)) << 10)`, a lower-precision (10-bit) variant that also fulfills the intent. The no_gui clock_gettime path (the active non-Windows implementation, `no_gui/source/time/no_gui_time.c:64`, duplicated in `tests/core/source/PLATFORM.c:87`) does NOT fulfill the intent: it returns a value derived from the absolute baseline timestamp rather than the per-call delta, as detailed below.

### Implementation Correctness
- **no_gui clock_gettime path — broken return / overflow.** At `no_gui/source/time/no_gui_time.c:80`, `timespec__current.tv_sec` is overwritten with the baseline (`timespec__current.tv_sec = _NO_GUI_timespec__initial.tv_sec;`) before `elapsed__seconds` is computed as `subtract_u32__no_overflow(timespec__current.tv_sec, get_time_elapsed_from__timer_u32(p_timer__seconds__u32))`. Because `timespec__current.tv_sec` now holds the (large) baseline seconds rather than the elapsed delta, `elapsed__seconds` is dominated by the baseline magnitude, not the true elapsed seconds. The `!elapsed__seconds` fallback further sets `elapsed__seconds = timespec__current.tv_sec + p_timer__seconds__u32->remaining__u32`, which is also baseline-dominated. The final `return (elapsed__seconds << 20) + ...` then overflows `u32F20` (baseline seconds << 20 far exceeds `UINT32_MAX`). The nanosecond borrow in the `if/else` is also inverted: it computes `initial.tv_nsec - current.tv_nsec` instead of the correct `current.tv_nsec + 1e9 - initial.tv_nsec`. The computed `elapsed__seconds`/`elapsed__nanoseconds` are then fed back into `progress_timer__u32`, corrupting both timers. This exact defective code is duplicated verbatim in the test stub (`tests/core/source/PLATFORM.c:87-121`). The commented-out SDL clock_gettime variant (`sdl/source/time/sdl_time.c:106`) avoids the `.tv_sec = baseline` overwrite and is the structurally-correct reference. Net effect: the no_gui/Unix default path does not return elapsed time and overflows.
- **NDS return-type mismatch.** `nds/source/time/nds_timer.c:9` defines the function returning `i32F20` (signed `int32_t`), while the header declares `u32F20` (unsigned `uint32_t`); these are not compatible types in C (different signedness). The NDS build includes `platform.h` widely (e.g. `nds/source/nds_main.c:9`), so callers rely on the `u32F20` declaration while the definition yields a signed value, and the `<< 20` shift has implementation-defined behavior for large uptimes once the high bit is set.
- **SDL non-Windows accumulators fed absolute uptime.** `sdl/source/time/sdl_time.c:66` calls `progress_timer__u32(p_timer__seconds__u32, total_miliseconds / 1000)` passing the *absolute* uptime seconds rather than the per-call delta. Because the timer's `start` is the huge sentinel `UINT32_MAX`, this does not wrap, so the timer's `start - remaining` ("elapsed") reading accumulates the *sum of all absolute uptimes* instead of true elapsed seconds; any consumer of `get_time_elapsed_from__timer_u32(time__seconds__u32)` reads a diverging value. The same absolute-vs-delta issue affects the nanoseconds timer (`(total_miliseconds % 1000) * 1000000`). The returned u32F20 delta (computed from `_SDL_miliseconds_last`) is still correct; only the accumulators are corrupted.
- **Type compatibility (declaration).** Return type `u32F20` (`uint32_t`, `core/include/defines.h:66` / `defines_weak.h:43`) matches the documented u32F20 semantics. Parameters `Timer__u32 *` (`defines_weak.h:125`: `{uint32_t remaining__u32; uint32_t start__u32;}`) match the header exactly. `Quantity__u32` passed to `progress_timer__u32` is `uint32_t` (`defines.h:140` / `defines_weak.h:49`), matching the parameter type; no implicit conversion or truncation.
- **Validation.** No null-checking is performed, matching the Lavender platform-layer convention; passing a null `Timer__u32 *` is undefined behavior (immediate dereference) and is the caller's responsibility. `poll_elapsed_time__u32F20_of__game` (`core/source/game.c:629`) always passes valid `&p_game->time__seconds__u32` / `&p_game->time__nanoseconds__u32`.

### Side Effects
Mutates both `Timer__u32` accumulators in-place via `progress_timer__u32` (and, on NDS, `loop_timer_u32`). Updates module-level baseline state (`_SDL_miliseconds_last` on the SDL non-Windows path; on the Windows/timeGetTime backends the baseline is the timer's stored prior value). No heap allocation, no I/O, and no other externally visible state is touched; the function's own observable effects are the in-place timer advance and the returned delta.
