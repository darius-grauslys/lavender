# open_ui_window_with__this_uuid_and__parent_uuid

**File of origin:** `core/source/ui/ui_context.c`

---

## Semantic

Opens a UI window with a caller-specified UUID and parent UUID by delegating to the internal `_open_ui_window` helper, passing a hardcoded UI element offset of `0`. This is a thin convenience wrapper that allows callers to specify both the graphics window UUID and its parent's UUID in a single call.

---

## Pre-conditions

1. `p_game` must be non-null. This is only checked in debug builds (`#ifndef NDEBUG`) inside `_open_ui_window`; in release builds, a null `p_game` would cause undefined behavior via null pointer dereference when calling `get_p_gfx_context_from__game(p_game)`.
2. `the_kind_of__graphics_window_to__open` must be a valid `Graphics_Window_Kind` enum value less than `Graphics_Window_Kind__Unknown`. This is bounds-checked inside `get_p_ui_window_record_from__ui_context`, which returns null (and logs an error) if the kind is out of range.
3. The `UI_Window_Record` corresponding to `the_kind_of__graphics_window_to__open` must have been previously registered via `register_ui_window_into__ui_context`, meaning both `f_ui_window__load` and `f_ui_window__close` function pointers must be non-null. This is validated by `is_ui_window_record__valid`.
4. `uuid_of__graphics_window__u32` can be any valid `Identifier__u32`. If it equals `IDENTIFIER__UNKNOWN__u32` (i.e., `(uint32_t)(-1)`), a new UUID is auto-generated by the graphics window manager; otherwise the specified UUID is used.
5. `uuid_of__parent_for__graphics_window__u32` can be any `Identifier__u32`. If a graphics window with this UUID exists in the window manager, it becomes the parent; if no matching parent is found, no parent-child relationship is established (the function silently proceeds without a parent).

---

## Post-conditions

1. On success, returns a non-null pointer to the newly allocated `Graphics_Window` struct.
2. On failure (null `p_game` in debug, invalid window kind, unregistered/invalid UI window record, or graphics window allocation failure), returns `NULL` (the wrapper passes through the return value of `_open_ui_window`, which returns `false`/`0` on error).
3. A new `Graphics_Window` is allocated from the graphics window manager with texture size `TEXTURE_FLAG__SIZE_256x256`.
4. If a parent window was found, the parent-child relationship is established via `set_graphics_window_as__parent_to__this_graphics_window`.
5. Depending on the signed quantities stored in the `UI_Window_Record`:
   - If `signed_quantity_of__ui_elements > 0`: a new UI manager is allocated for this window.
   - If `signed_quantity_of__ui_elements < 0`: the parent's UI manager is shared with this window (only if a parent exists).
   - If `signed_quantity_of__sprites > 0`: a new sprite manager is allocated for this window.
   - If `signed_quantity_of__sprites < 0`: the parent's sprite manager is shared with this window (only if a parent exists).
6. The window is populated with UI elements via `populate_window_with__ui`, which invokes the registered `f_ui_window__load` handler, enables the window, and marks it as needing composition.

---

## Correctness Verdict

**Correct**

The wrapper function correctly delegates to `_open_ui_window` with the appropriate parameters. The hardcoded `index_of__ui_element_offset__u16 = 0` is a valid design choice for this convenience wrapper, allowing callers who don't need a UI element offset to use a simpler API. The function faithfully passes through all caller-provided parameters and the return value from `_open_ui_window`.

---

## Semantic Alignment

The implementation fulfills its semantic intent: it provides a simplified entry point for opening a UI window with both a UUID and parent UUID specified, without requiring the caller to provide a UI element offset. The function does nothing beyond delegating to `_open_ui_window`, which is the correct behavior for a wrapper function. No semantic drift is present.

---

## Implementation Correctness

- **Type compatibility:** The return type `Graphics_Window *` is compatible with the return value of `_open_ui_window`, which returns `Graphics_Window *`. However, `_open_ui_window` returns `false` (i.e., `0`) on error paths, which implicitly converts to a null pointer. While this is valid C (since `false` is defined as `0` in `<stdbool.h>` and `0` is a valid null pointer constant), it is not idiomatic; returning `NULL` or `0` directly would be clearer. This is a minor style issue in `_open_ui_window`, not in the wrapper itself.
- **Undefined behavior:** No undefined behavior is introduced by this wrapper function. The null check for `p_game` is delegated to `_open_ui_window` (debug builds only). The bounds checking for `the_kind_of__graphics_window_to__open` is handled by `get_p_ui_window_record_from__ui_context`.
- **Validation:** The wrapper performs no validation itself, which is appropriate for a thin delegation wrapper. All meaningful validation is performed inside `_open_ui_window` and its callees. The debug-only null check for `p_game` follows the codebase convention of only validating in debug builds.

---

## Side Effects

This function has no side effects of its own beyond those of `_open_ui_window`, which it delegates to. The observable side effects are:

- Allocates a new `Graphics_Window` in the graphics window manager's pool.
- Possibly allocates a UI manager and/or sprite manager for the new window (depending on the `UI_Window_Record`'s signed quantities).
- Possibly shares the parent's UI manager and/or sprite manager with the new window.
- Invokes the registered `f_ui_window__load` handler, which populates the window with UI elements.
- Marks the graphics window as enabled and in need of composition.
