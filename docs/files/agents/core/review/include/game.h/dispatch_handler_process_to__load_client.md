dispatch_handler_process_to__load_client — core/source/game.c

Dispatches (runs) the game's registered "deserialize client" process handler against the client identified by UUID, opening the client's file on disk and binding the resolved Client to the new Process via a filesystem serialization request.

Pre-conditions:
1. p_game must be a non-null pointer to a valid, initialized Game object (its process_manager and platform filesystem context must be initialized). Null-checking p_game is the caller's responsibility and is not performed here (engine convention).
2. path_to__client_file must be a valid, null-terminated IO_path (char[MAX_LENGTH_OF__IO_PATH]) naming the file to open. The mode string is interpreted by the platform layer.
3. uuid_of__client__u32 must identify a Client that already exists in the game's client pool (previously allocated); get_p_client_by__uuid_from__game returns null otherwise.
4. p_game->m_process__deserialize_client must be non-null (registered via set_dispatch_handler_process_for__load_client); otherwise the function bails early and returns 0.
5. The process manager must have available capacity for a new Process (PROCESS_MAX_QUANTITY_OF); run_process returns 0 when the pool is exhausted.
6. p_game->m_process__deserialize_client is of type m_Process (void (*)(Process*, Game*)), matching run_process's expected handler signature.
7. The file mode "w+b" is passed to the filesystem initializer with is_accepting__non_existing_file=true, so a missing file is tolerated (returns success, per initialize_process_as__filesystem_process__open_file's File_Not_Found handling); an existing file is truncated on open.

Post-conditions:
1. On success: a new Process is allocated and enqueued in the game's process manager, scheduled at maximum priority (PROCESS_PRIORITY__0_MAXIMUM) with PROCESS_FLAG__IS_CRITICAL; the Process * is returned to the caller, which becomes its owner.
2. On success: the returned Process's p_process_data points to a freshly allocated Serialization_Request (installed by initialize_process_as__filesystem_process), and that request's p_data points to the resolved Client (p_client), bound via initialize_process_as__filesystem_process__open_file -> initialize_process_as__filesystem_process; a filesystem dispose handler is installed on the process.
3. On failure — handler not registered: returns 0; no state mutation (client lookup has not yet been performed).
4. On failure — client not found (get_p_client_by__uuid_from__game returns null): returns 0; no state mutation.
5. On failure — process allocation (run_process returns 0) or filesystem initialization fails: returns 0; the resolved Client is marked failed-to-load via set_client_as__failed_to_load (clears client_flags__u16, sets CLIENT_FLAG__IS_FAILED_TO_LOAD); the newly allocated Process is released back to the process manager via release_process_from__process_manager (dispose handler invoked, slot reset). When run_process itself returned 0, release_process_from__process_manager receives a null Process and is a validated no-op.
6. No mutation occurs to the client pool structure, the Client's gameplay/core fields, or the handler callback in any path. (Only the Client's client_flags__u16 is mutated, solely on the failure path via set_client_as__failed_to_load.)

Correctness Verdict: Correct

Semantic Alignment:
The function does exactly what its name implies — it dispatches the registered deserialize-client (load-client) process handler against an existing client: it validates the handler is registered, resolves the target client by UUID, spawns a critical maximum-priority process, opens the client file as a filesystem serialization request bound to that client, and returns the process. The implementation fulfills the dispatch-level semantic intent; this is a launcher/dispatch, not a struct initializer, so the Lavender initialization-vs-RAII distinction does not apply here (the deserialize handler itself performs whatever client data loading it performs).

One observed concern: the file is opened with mode "w+b" (write+read+binary+truncate), which on open truncates an existing file to zero length. For a load (deserialize) operation this is semantically suspect, and the inline TODO ("only read mode, cache client data into single file") explicitly acknowledges the intent to switch to a read-only mode. Definitive judgment on whether this causes data loss depends on the platform layer's open_file semantics and the deserialize handler's read/write ordering, which are callee responsibilities and therefore out of scope for this review; this is flagged as a noted item rather than a structural defect.

Implementation Correctness:
- Type compatibility: every argument matches its target. p_game->m_process__deserialize_client (m_Process) is passed as run_process's m_Process parameter; PROCESS_PRIORITY__0_MAXIMUM (macro 0) is passed to uint32_t priority_level (0 fits, no truncation); PROCESS_FLAG__IS_CRITICAL (BIT(0) = 1) is passed to Process_Flags__u8 (uint8_t, 1 fits, no truncation); path_to__client_file (IO_path = char[MAX_LENGTH_OF__IO_PATH]) is passed to initialize_process_as__filesystem_process__open_file's IO_path parameter (decay to const char* / char* compatible); the string literal "w+b" (const char[4]) is passed to the const char *p_file_descriptors parameter; p_client (Client *) is passed as void *p_serialization_request__data (any object pointer assignable to void *); uuid_of__client__u32 (Identifier__u32) matches get_p_client_by__uuid_from__game's parameter; get_p_process_manager_from__game returns Process_Manager * matching run_process's first parameter and release_process_from__process_manager's second parameter; run_process's Process * return is assigned to Process * p_process.
- Undefined behavior: none introduced. No pointer arithmetic, no type punning, no out-of-bounds access. p_process is only dereferenced after validation inside initialize_process_as__filesystem_process__open_file (which null-checks p_process before use) and inside release_process_from__process_manager (which validates its Process * argument). p_game is dereferenced for member access; null p_game is a caller-violated pre-condition (consistent with the engine convention that p_game null-checking is the caller's responsibility and is not performed in game.c dispatchers). get_p_client_by__uuid_from__game and get_p_process_manager_from__game are only invoked on a valid p_game.
- Validation: appropriate for a dispatch handler. The function checks (a) the handler is registered, (b) the client was found, and (c) process allocation / filesystem initialization succeeded. The latter two are meaningful because run_process returns 0 when the process pool is exhausted, and initialize_process_as__filesystem_process__open_file returns false on p_process==null, serialization-request allocation failure, or a file-open error other than tolerated File_Not_Found. Each failure path returns 0 and logs an error; only the post-allocation failure paths mutate the client (marks failed-to-load) and release the process. The caller is responsible for validating p_game and the path/UUID inputs.

Side Effects:
- Mutates the game's Process_Manager: allocates and enqueues a new entry in its process table via run_process (the primary observable effect); installs a filesystem dispose handler on the process and a heap Serialization_Request as the process's p_process_data.
- On the filesystem-init / allocation failure path: mutates the resolved Client's client_flags__u16, clearing all flags and setting CLIENT_FLAG__IS_FAILED_TO_LOAD via set_client_as__failed_to_load; releases the newly allocated Process back to the process manager via release_process_from__process_manager (dispose handler runs, slot reset, and — when a serialization request was allocated on the open-file-error path — it is released by initialize_process_as__filesystem_process__open_file before returning).
- Binds the resolved Client * as the Serialization_Request's p_data (the process's p_process_data points to that request, not directly to the client).
- Opens the file at path_to__client_file with mode "w+b" (platform-layer side effect: may create or truncate the file), tolerated for File_Not_Found.
- Emits log output: debug_error for an unregistered handler, for a missing client, and for each failure path (failed-to-run-process).
- Does not mutate the client pool structure, the Client's gameplay/core fields, or any handler callback.
