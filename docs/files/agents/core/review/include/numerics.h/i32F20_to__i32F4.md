i32F20_to__i32F4 — core/include/numerics.h

Converts a 20-bit fractional fixed-point value (i32F20) to a 4-bit fractional fixed-point value (i32F4) by performing an arithmetic right shift of 16 bits (the difference in fractional precision: 20 - 4 = 16).

Pre-conditions:
1. x is any valid i32F20 value (a 32-bit signed integer with 20 bits of fractional precision). No range constraint or null check required — the parameter is passed by value.

Post-conditions:
1. The returned Signed_Index__i32 value is the result of arithmetically right-shifting x by 16 bits, yielding the equivalent value in i32F4 fixed-point representation.
2. The sign of negative inputs is preserved via the ARITHMETRIC_R_SHIFT macro.

Correctness Verdict: Correct

Semantic Alignment:
The function correctly converts from i32F20 to i32F4. The conversion requires shifting right by (20 - 4) = 16 bits to account for the reduced fractional precision. The function uses FRACTIONAL_PERCISION_16__BIT_SIZE (which is 16) as the shift amount, which is correct. The ARITHMETRIC_R_SHIFT macro properly handles negative numbers by performing an arithmetic right shift, preserving the sign bit. This is consistent with all other F-to-F conversion functions in the file (e.g., i32F20_to__i32F8 shifts by 12, i32F4_to__i32F20 shifts left by 16).

Implementation Correctness:
Type compatibility — the parameter x is of type i32F20 (typedef int32_t) and the return type is Signed_Index__i32 (typedef int32_t). Both are 32-bit signed integers with identical representation, so there is no implicit conversion, truncation, or type mismatch. The ARITHMETRIC_R_SHIFT macro operates on i32 and produces i32, which is compatible with the return type.
No undefined behavior — the ARITHMETRIC_R_SHIFT macro avoids undefined behavior from right-shifting negative numbers by branching: for non-negative values it uses a direct right shift, and for negative values it negates, right-shifts, then negates the result. No pointer arithmetic, no null dereference, no type punning, no out-of-bounds access.
No validation is needed — this is a pure arithmetic computation on a value parameter. Validation is the caller's responsibility.
